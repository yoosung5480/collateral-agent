## 1. 한 줄 요약

`담보물배분표`는 `datas/`의 등기부등본 PDF, 감정평가서 PDF, 공장저당법목록 PDF를 **반드시 LLM API로 구조화**한 뒤, 단계별 JSON 산출물(`pipeline_artifacts/`)로 등기부·감정평가·저당목록 정보를 대조하고, 검증된 `workbook_plan.json`만 사용해 최종 `담보물배분표.xlsx`를 생성하는 회계 담보물 배분표 자동작성 프레임워크다.

가장 중요한 운영 원칙은 다음이다.

1. **LLM API 호출 없는 성공은 성공이 아니다.** fallback 실행은 시스템 실패로 취급한다.
2. LLM은 PDF 판독·의미 대조를 담당하되, **금액 합산·수량 합계·Excel 좌표·서식·저장은 코드가 결정론적으로 수행**한다.
3. 최종 Excel은 직접 PDF를 다시 읽지 않고, `pipeline_artifacts/05_excel/workbook_plan.json`을 검증한 뒤 `excel.write_collateral_workbook()`으로 작성한다.
4. `review_required` 또는 `blocking_errors`가 남아 있는 plan은 최종 Excel 확정 대상으로 보면 안 된다.

## 2. 절대 준수해야 할 제약

### 2.1 fallback 금지

현재 사용자의 명시 요구는 “항상 LLM API를 사용해야 하며, fallback 실행은 시스템 실패”이다.

- `main.py`의 현재 통합 실행 경로는 `registry/main.py`의 fixture fallback을 사용하지 않고, `RawRegistryParser`, `RegistryParser`, `AppraisalParser`, `MortgageParser`를 직접 LLM 객체와 함께 호출한다.
- 단, `registry/main.py`에는 과거 호환용 `allow_fixture_fallback=True` 경로와 fixture 관련 코드가 존재한다. **통합 실행 또는 신규 agent 작업에서는 이 경로를 성공 경로로 사용하면 안 된다.**
- `.env`에 `OPENAI_API_KEY`가 없거나 API 호출이 실패하면, 조용히 기존 JSON이나 fixture로 대체하지 말고 실패로 드러나야 한다.

### 2.2 코드와 LLM의 책임 분리

| 책임 | 담당 | 설명 |
| --- | --- | --- |
| PDF 경계/구간 판정 | LLM + Pydantic 스키마 | 등기부 분리, 감정평가 명세표 구간, 저당목록 번호별 구간 |
| PDF 내용 구조화 | LLM + Pydantic 스키마 | 표제부, 을구, 토지·건물, 기계기구, 저당목록 현재 유효 품목 |
| 등기부 그룹 병합 | 코드 | 날짜·금액·담보권자·공담·목록번호 정규화 후 동일 담보설정현황 판정 |
| 부동산 감정평가 그룹 매칭 | LLM 판단 + LLM 검증 + 코드 확정 | LLM은 ID 관계만 반환, 코드는 원본 금액 재조회·합산 |
| 기계기구-저당목록 대조 | LLM 판단 + 코드 O/X/null 변환 | LLM은 item ID 대응만 반환, 코드는 수량 소비와 membership 행렬 생성 |
| 합계/검산 | 코드 | 부동산 평가액, 기계 수량·금액, unit_price × quantity 검산 |
| Excel 작성 | 코드/openpyxl | 행 커서, 병합, 스타일, 서식, 수식, 저장 |

## 5. 통합 실행 흐름(`main.py`)

`main.py`의 `main()`은 아래 순서로 실행된다.

```text
1. PDF 렌더러 설정
2. LLM 3개 생성
   - gpt_mini: 구간/경계 탐지용 gpt-5.4-mini
   - gpt_sol: 문서 내용 추출용 gpt-5.6-sol
   - gpt_tool: pipeline 의미 매칭용 gpt-5.6-sol, reasoning_effort="none"

9. excel.write_collateral_workbook(workbook_plan, FINAL_OUTPUT_PATH) 실행
10. 최종 xlsx 저장 및 manifest 경로 출력
```

## 7. 문서별 parser 프레임워크

### 7.1 등기부등본(`registry/`)

핵심 파일:

- `registry/pdf_llm_parser.py`: 원본 등기부 PDF를 여러 등기부 단위로 나누고, 각 등기부에서 표제부/을구 PDF만 선택 저장한다.
- `registry/parse_registry_info.py`: 선택된 표제부/을구 PDF를 LLM으로 읽어 `title.json`, `encumbrance.json`을 생성한다.
- `registry/json_model.py`: Pydantic 모델 공통 JSON 저장/로드 유틸.
- `registry/main.py`: 과거 통합 워크플로우. fixture fallback 코드가 있으므로 현재 통합 실행에서는 사용하지 않는 것이 안전하다.

등기부 처리 흐름:

```text
REGISTRY_PDF_PATH
  → RawRegistryParser.find_registry_start_pages()
  → registry_XX_pS-E 단위 PDF 범위 계산
  → RawRegistryParser.find_section_pages()
  → title.pdf / encumbrance.pdf 저장
  → RegistryParser.extract_title() → title.json
  → RegistryParser.extract_encumbrance() → encumbrance.json
```

`title.json` 주요 계약:

```json
{
  "registry_id": "출처 분할 PDF 경로 또는 registry 식별자",
  "property_type": "토지 | 건물",
  "location": "현재 유효 소재지",
  "details": "말소/과거 이력 제외한 현재 유효 내역"
}
```

`encumbrance.json` 주요 계약:

```json
{
  "registry_id": "출처 분할 PDF 경로 또는 registry 식별자",
  "mortgages": [
    {
      "registration": "최초 근저당권 설정 접수일자",
      "maximum_claim": "채권최고액 원문",
      "mortgagee": "근저당권자",
      "shared_collateral": "공용담보/공동담보/공담 또는 빈 문자열",
      "mortgage_list_no": "공장 및 광업재단 저당법 제6조 목록 번호 또는 빈 문자열"
    }
  ]
}
```

주요 판정 규칙:

- 말소·해지·취소선 권리는 제외한다.
- 을구는 현재 유효한 근저당권만 추출한다.
- 부기등기는 별도 권리로 만들지 않고 원등기에 반영한다.
- `registration`은 변경등기일이 아니라 최초 설정 접수일자다.

### 7.2 감정평가서(`appraisal/`)

핵심 파일:

- `appraisal/parser.py`: 감정평가서 전체 워크플로우가 대부분 이 파일에 있다.
- `appraisal/README.md`: 토지·건물/기계기구 추출 규칙 상세 설명.
- `appraisal/report.md`: 구현 보고서.

감정평가서 처리 흐름:

```text
APPRAISAL_PDF_PATH
  → AppraisalSectionSplitter.find_section_pages()
  → 토지·건물 감정평가명세표.pdf 저장
  → 기계기구 감정평가명세표.pdf 저장
  → AppraisalContentExtractor.extract_land_building()
  → AppraisalContentExtractor.extract_machinery()
  → output/appraisal/{감정평가서 stem}.json 저장
```

특징:

- 구간 탐지에는 원본 PDF와 함께 PyMuPDF/Pillow로 만든 contact sheet 이미지가 들어간다. 빨간 `PDF PAGE N` 라벨을 기준으로 물리 페이지를 판정한다.
- 내용 추출에는 PDF 원본과 각 페이지 고해상도 이미지가 함께 들어간다.
- 토지·건물 그룹은 `location_lot_number` 기준으로 묶는다.
- `total_appraised_value`는 그룹의 `items[].appraised_value` 합계여야 한다.
- 기계기구는 합계/주석/이하 여백 행을 품목으로 만들지 않는다.
- 문서에 없는 값은 추정하지 않고 `null`로 둔다.

감정평가 JSON 주요 계약:

```json
{
  "land": [
    {
      "location_lot_number": "소재지 지번",
      "total_appraised_value": 123,
      "items": [
        {
          "location": "소재지",
          "lot_number": "지번",
```

## 8. pipeline 단계별 산출물(`pipeline.py`)

`pipeline.py`는 세 parser가 만든 JSON을 바탕으로 최종 Excel 입력 plan을 만든다. 모든 단계 산출물은 `PIPELINE_OUTPUT_ROOT` 아래에 저장된다.

현재 실행 산출물 구조 예시:

```text
{APPRAISAL_PDF_PATH.stem}/pipeline_artifacts/
├── run_manifest.json
├── 01_registry_merge/
│   ├── merged_title.json
│   ├── merged_encumbrance.json
│   └── merge_validation.json
├── 02_real_estate/
│   ├── real_estate_match_decisions.json
│   ├── real_estate_match_verification.json
│   └── real_estate_table_plan.json
├── 03_machinery_base/
│   └── machinery_distribution_base.json
├── 04_machinery_match/
│   ├── list_match_{YYYY_N}.json
│   ├── machinery_match_verification.json
│   └── machinery_table_plan.json
└── 05_excel/
    ├── workbook_plan.json
    └── workbook_validation.json
```

### 8.1 `build_manifest()`

목적: 한 실행에 사용할 원천 JSON 경로를 명시한다. 폴더를 재귀 탐색하지 않는다.

입력:

- `run_id`
- `borrower_name`
- 등기부 `title_json`/`encumbrance_json` 쌍 목록
- 감정평가 JSON 경로
- 저당목록 JSON 경로
- 최종 Excel 출력 경로

산출 주요 필드:

```json
{
  "run_id": "...",
  "borrower_name": "...",
  "registries": [
    {"title_path": ".../title.json", "encumbrance_path": ".../encumbrance.json"}
  ],
  "real_estate_appraisal_path": "...",
  "machinery_appraisal_path": "...",
  "mortgage_lists_path": "...",
  "mortgage_lists": [
    {"mortgage_list_no": "...", "path": "..."}
  ],
  "output_path": ".../담보물배분표.xlsx"
}
```

### 8.2 Stage 1: `stage1_merge_registry()`

목적: 여러 등기부의 표제부와 을구를 정확히 연결하고, 담보설정현황이 같은 등기부를 같은 그룹으로 병합한다.

핵심 정규화:

- `registry_id`: `registry_01`, `registry_02` 형식으로 정규화
- 날짜: `YYYY-MM-DD`
- 금액: 정수
- 공담: `공용담보`, `공동담보`, `공담`, OCR 오타 `공동탐보` → 비교용 `공담`
- 근저당권자: 비교 시 `주식회사` 접두어와 공백 제거
- 저당목록 번호: `제YYYY-N호` 형식 정규화

동일 담보설정현황 signature:

```text
(registration, maximum_claim, mortgagee, shared_collateral, mortgage_list_no, source_order)
```

산출물:

- `merged_title.json`: `group_id`, `registry_ids`, `properties`
- `merged_encumbrance.json`: `group_id`, `registry_ids`, 날짜순 `mortgages`와 rank
- `merge_validation.json`: registry 개수, group 개수, 상태

### 8.3 Stage 2: `stage2_real_estate()`

목적: 등기부 부동산 그룹과 감정평가서 토지·건물 그룹을 의미적으로 대조하고, 부동산 담보물 배분표 plan을 만든다.

흐름:

1. `build_real_estate_appraisal_groups()`가 감정평가 `land`, `building` 그룹에 안정 ID를 부여한다.
   - `land_001`, `land_002`, ...
   - `building_001`, `building_002`, ...
2. `run_real_estate_matching()`이 LLM에게 `merged_title.groups`와 감정평가 그룹 ID 목록을 전달한다.
3. LLM은 `RealEstateMatchDecision` 스키마로 `appraisal_group_id → target_group_id` 관계만 반환한다.
4. `verify_real_estate_matching()`이 별도 LLM 호출로 1차 assignment를 검증한다.
5. 코드는 승인된 ID만 원본 감정평가 JSON에서 다시 조회해 `total_appraised_value`를 합산한다.
6. 결정론적 보정 `_resolve_unassigned_buildings()`가 같은 지번의 건물/제시외건물 묶음 등 현재 구현된 특수 케이스를 처리한다.

중요 불변조건:

- 같은 감정평가 group ID는 한 번만 사용 가능하다.
- LLM이 반환한 금액은 사용하지 않는다. 가능한 스키마에도 금액 필드를 두지 않는다.
- 하드 충돌, 검증 미승인, 중복 배정은 `review_required`로 간다.
- `status != ok`이면 최종 Excel 확정 대상이 아니다.

`real_estate_table_plan.json` 주요 필드:

```json
{
  "status": "ok",
  "real_estate_tables": [
    {
      "group_id": "group_01",
      "registry_ids": ["registry_01"],
      "mortgagee": "...",
      "properties": [ ... ],
      "mortgages": [ ... ],
      "appraisal_matches": [
        {
          "appraisal_group_id": "land_001",
          "property_type": "토지",
          "location_lot_number": "...",
          "appraised_value": 123,
          "decision": "matched",
          "reason": "...",
          "evidence": ["..."]
        }
      ],
      "total_appraised_value": 123,
      "allocation_amount": null,
      "allocation_balance": null
    }
  ],
  "review_required": [],
  "blocking_errors": []
}
```

### 8.4 Stage 3: `stage3_machinery_base()`

목적: 기계기구 배분표의 기준이 되는 담보 그룹과 저당목록 번호 목록을 선택한다.

선택 규칙:

- `merged_encumbrance.groups`의 각 그룹에서 비어 있지 않은 `mortgage_list_no` 집합을 만든다.
- 저당목록 JSON에 존재하는 목록번호 집합의 부분집합이면서, 목록번호 개수가 최대인 후보를 찾는다.
- 유일한 최대 후보가 아니거나 목록번호가 없으면 `ValueError`로 실패한다.

산출물 `machinery_distribution_base.json`:

```json
{
  "status": "ok",
  "source_group_id": "group_01",
  "registry_ids": ["registry_01"],
  "locations": ["..."],
  "properties": [ ... ],
  "mortgages": [ ... ],
  "mortgage_list_numbers": ["공장 및 광업재단 저당법 제6조 목록 제YYYY-N호"],
  "review_required": [],
  "blocking_errors": []
}
```

### 8.5 Stage 4: `stage4_machinery_match()`

목적: 감정평가서 기계기구 행을 기준으로 각 저당목록에 해당 기계가 포함되는지 대조하고, 기계기구 배분표 및 대조표 plan을 만든다.

흐름:

1. `build_machinery_appraisal_items()`가 감정평가 `machinery` 배열에 안정 ID를 부여한다.
   - `machine_001`, `machine_002`, ...
   - `appraisal_serial_no`는 배열 순서 기반 문자열
   - `amount`는 `appraised_value`로도 복사
   - `unit_price`와 `quantity`가 둘 다 있으면 `unit_price * quantity == amount`를 검산한다.
2. `build_mortgage_list_items()`가 각 저당목록 항목에 안정 ID를 부여한다.
   - `list_YYYY_N:item_001`, ...
3. 목록번호별로 `run_one_machinery_match()`를 병렬 호출한다(`ThreadPoolExecutor`, 최대 6개).
4. LLM은 `MortgageListMatchDecision`으로 item ID 관계만 반환한다.
5. `_resolved_machinery_cells()`가 LLM 후보를 `O`, `X`, `null`로 변환한다.
   - 동일 저당목록 item은 원문 수량 범위 안에서만 소비 가능하다.
   - 반복 품목은 감정평가 행 순서로 tie-break한다.
   - unresolved는 가능한 경우 conflicts/evidence에서 item 번호 또는 단일 동일 명칭 항목으로 제한적 보정한다.
6. 최종 `membership` 행렬을 만든다.

현재 Excel 값 규칙:

| 내부 판단 | `membership` 값 | Excel 셀 |
| --- | --- | --- |
| 확정 매칭 | `O` | `O` |
| 명시적 불일치 | `X` | `X` |
| 미해결/누락 | `null` | 공란 + `review_required` |

> 설계 문서 일부에는 “matched 외에는 공란”으로 적힌 부분이 있으나, 현재 코드(`excel.write_machinery_comparison_table`)는 `membership_values`가 `O` 또는 `X`이면 그대로 Excel에 쓴다. 따라서 현재 구현 기준으로는 `X`도 표시될 수 있다.

`machinery_table_plan.json` 주요 필드:

```json
{
  "status": "ok",
  "source_group_id": "group_01",
  "registry_ids": ["registry_01"],
  "locations": ["..."],
  "properties": [ ... ],
  "mortgages": [ ... ],
  "mortgage_list_numbers": ["..."],
  "quantity_total": 9,
  "total_appraised_value": 89330000,
  "comparison_rows": [
    {
      "appraisal_row_index": 1,
      "appraisal_item_id": "machine_001",
      "name": "...",
      "manufacturer": "...",
      "manufacture_date": "...",
      "quantity": 1,
      "unit_price": 123,
      "amount": 123,
      "membership": {"공장 및 광업재단 저당법 제6조 목록 제YYYY-N호": "O"},
      "match_evidence": {"...": {"matched_list_item_ids": ["..."]}}
    }
  ],
  "review_required": [],
  "blocking_errors": []
}
```

### 8.6 Stage 5: `build_workbook_plan()` 및 `validate_workbook_plan()`

목적: 부동산 plan과 기계기구 plan을 최종 Excel 작성용 단일 plan으로 합치고 검증한다.

`workbook_plan.json` 주요 필드:

```json
{
  "status": "ok",
  "borrower_name": "...",
  "sheet_name": "Sheet1",
  "real_estate_tables": [ ... ],
  "machinery_table": {
    "source_group_id": "...",
    "registry_ids": [ ... ],
    "locations": [ ... ],
    "properties": [ ... ],
    "quantity_total": 9,
    "total_appraised_value": 89330000,
    "mortgages": [ ... ]
  },
  "machinery_comparison": {
    "mortgage_list_numbers": [ ... ],
    "rows": [ ... ],
```

검증 기준:

- `blocking_errors` 비어 있음

- 기계기구 `amount_total == comparison rows amount 합계`
- 각 기계기구 행의 membership key 집합이 목록번호 집합과 일치
- `unit_price`, `quantity`가 모두 있으면 `unit_price * quantity == amount`

## 9. Excel 작성기(`excel.py`)

현재 최종 통합 실행에서 중요한 공개 함수는 `write_collateral_workbook(workbook_plan, output_path)`이다.

### 9.1 역할

`write_collateral_workbook()`은 고수준 Excel tool-call 역할을 한다.

- 입력 plan 검증(`_validate_workbook_plan()`)
- workbook/sheet 생성
- 기본 열 너비, zoom, grid 설정
- 부동산 담보물 배분표 작성
- 기계기구 담보물 배분표 작성
- 기계기구 대조표 작성
- 수식 재계산 설정
- 임시 파일 `.tmp.xlsx` 저장 후 최종 파일로 atomic replace

### 9.2 주요 내부 함수

| 함수 | 역할 |
| --- | --- |
| `_minimal_prototype()` | 별도 Excel template 없이 기본 서식 prototype workbook 생성 |
| `_write_title_row()` | `<부동산 담보물 배분표>`, `<기계기구 담보물 배분표>` 제목 행 작성 |
| `_write_common_headers()` | 담보물 소재지/내역/담보설정현황/가치평가액/배분내역 공통 헤더 작성 |
| `_write_mortgage_body()` | 본문 행, 담보설정 순위, 설정일자, 채권자, 공담, 설정금액 블록 작성 |
| `write_real_estate_collateral_table()` | 부동산 영역 한 그룹 작성 |
| `write_machinery_collateral_table()` | 기계기구 배분표 영역 작성 |
| `write_machinery_comparison_table()` | 기계기구 대조표 동적 목록번호 열 작성 |

### 9.3 Excel 레이아웃 핵심

`01_엑셀_구조도_설명서.md`와 `03_결과_엑셀_작성_지침서.md` 기준으로 구현되어 있다.

- workbook은 기본적으로 단일 sheet를 사용한다.
- 열 A:P는 고정 의미를 가진다.
- 기계기구 대조표는 J열 이후 저당목록 수만큼 동적 열이 늘어난다.
- 배분액/배분잔액은 원천 데이터가 없으므로 작성하지 않는다.
- 가치평가액은 plan에서 확정된 숫자만 쓴다.
- 기계기구 단가는 `unit_price`가 `null`이면 역산하지 않고 공란으로 둔다.

이전 산출물이 존재하므로, agent가 폴더 전체를 재귀 탐색해 최신 입력을 추론하면 잘못된 조합을 선택할 수 있다. **항상 `main.py` 상수와 `run_manifest.json`을 기준으로 파일 연결을 판단**해야 한다.

## 11. 실패/검토 필요 상태 해석

### 11.1 즉시 실패로 보아야 할 상황

- `OPENAI_API_KEY` 부재 또는 API 호출 실패를 fixture/기존 JSON으로 대체해 성공 처리한 경우
- `registry_id`를 추출하지 못한 경우
- title/encumbrance의 `registry_id`가 서로 다른 경우
- 같은 `registry_id`가 중복된 경우
- 근저당 날짜 또는 금액을 파싱할 수 없는 경우
- 기계기구 기준 담보 그룹을 유일하게 선택할 수 없는 경우
- `unit_price * quantity != amount`인 기계기구 감정평가 행이 있는 경우
- `workbook_plan.status != ok`
- `review_required` 또는 `blocking_errors`가 비어 있지 않은 경우
- `workbook_validation.status != ok`

### 11.2 사람이 검토해야 할 가능성이 높은 상황

- 등기부 동일 담보설정현황 signature가 애매하게 갈라지는 경우
- 부동산 주소/지번 토큰이 충돌하는데 LLM이 matched로 판단한 경우
- LLM 1차 부동산 assignment와 검증 결과가 불일치하는 경우
- 감정평가 그룹 하나가 둘 이상의 담보 그룹에 들어간 경우
- 저당목록 항목 후보가 복수인 경우
- 기계기구 반복 품목에서 제작자/제작연월/수량 일부가 누락된 경우
- 저당목록 JSON의 목록번호와 을구의 목록번호 집합이 맞지 않는 경우

## 13. 유지보수 가이드

### 13.1 새 입력 PDF로 바꾸는 방법

현재 설계는 외부 인자가 아니라 `main.py` 최상단 상수를 직접 수정하는 방식이다. 새 케이스로 전환하려면 다음 상수를 함께 맞춰야 한다.

```python
REGISTRY_PDF_PATH = PROJECT_ROOT / "datas" / "...pdf"
APPRAISAL_PDF_PATH = PROJECT_ROOT / "datas" / "...pdf"
MORTGAGE_LIST_PDF_PATH = PROJECT_ROOT / "datas" / "...pdf"
MORTGAGE_LIST_JSON_PATH = MORTGAGE_LIST_OUTPUT_ROOT / f"{MORTGAGE_LIST_PDF_PATH.stem}.json"
RUN_ID = ...
BORROWER_NAME = ...
FINAL_OUTPUT_DIR = PROJECT_ROOT / APPRAISAL_PDF_PATH.stem
FINAL_OUTPUT_PATH = FINAL_OUTPUT_DIR / "담보물배분표.xlsx"
PIPELINE_OUTPUT_ROOT = FINAL_OUTPUT_DIR / "pipeline_artifacts"
```

변경 시 주의:

- 이전 `output/registry`에 다른 케이스의 `registry_XX` 결과가 남아 있을 수 있으므로 manifest가 실제 이번 실행 결과만 참조하는지 확인한다.
- `run_registry_workflow()`는 이번 실행의 `registry_results`만 manifest에 넣으므로 통합 경로를 그대로 쓰면 폴더 잔여물에 덜 취약하다.
- 사람이 수동으로 pipeline 함수를 호출할 때는 반드시 `build_manifest()` 입력이 현재 케이스의 JSON만 가리키게 해야 한다.

### 13.2 prompt 또는 schema 수정 시

- Pydantic 모델 필드명은 downstream pipeline이 직접 참조한다. 이름을 바꾸면 `pipeline.py`와 `excel.py`를 같이 확인해야 한다.
- LLM에게 금액 합계나 Excel 좌표 생성을 맡기지 말아야 한다.
- 추출 prompt를 완화하면 말소/변경 이력이 현재 유효 데이터로 섞일 위험이 크다.
- `structured_output` 스키마에 optional을 늘리는 경우, downstream 검증에서 `null` 처리 규칙을 명시해야 한다.

### 13.3 Excel 수정 시

- 범용 셀 쓰기 도구처럼 바꾸지 말고, `workbook_plan`을 입력으로 받는 고수준 작성 방식을 유지한다.
- 행 커서와 병합 범위는 `excel.py` 내부 함수가 소유한다.
- 배분액/배분잔액은 현재 원천 데이터가 없으므로 공란 유지가 정답이다.
- `unit_price=null`인 기계기구 행은 역산하지 않는다.
- 동적 저당목록 열 수가 16열을 초과할 수 있으므로 `max_columns = max(16, 9 + 목록번호 수)` 패턴을 유지한다.

## 14. agent/LLM 인수인계 체크리스트

새 agent가 이 프레임워크를 이어받으면 아래 순서로 확인한다.

1. `main.py`의 하드코딩 상수가 현재 목표 PDF를 가리키는지 확인한다.
2. `.env`에 `OPENAI_API_KEY`가 있어 실제 LLM API 호출이 가능한지 확인한다. 키 값은 로그/문서에 노출하지 않는다.
3. `registry/main.py`의 fixture fallback 경로를 통합 성공 경로로 사용하지 않는다.
4. `python main.py` 실행 후 `pipeline_artifacts`의 각 단계 status를 확인한다.
5. `workbook_plan.status`, `review_required`, `blocking_errors`, `workbook_validation.status`를 확인한다.
6. 최종 `담보물배분표.xlsx`가 `FINAL_OUTPUT_PATH`에 생성되었는지 확인한다.
7. 문제 발생 시 Excel부터 고치지 말고, 어느 stage의 JSON에서 의미 오류가 생겼는지 역추적한다.
8. 부동산 금액/기계 수량·금액 오류는 LLM prompt보다 먼저 코드 검산과 원본 JSON 값을 확인한다.
9. 저당목록 O/X 오류는 `04_machinery_match/list_match_*.json`과 `machinery_table_plan.json`의 `match_evidence`를 함께 본다.
10. 최종 보고 시 “fallback 없이 LLM API 기반으로 실행되었는지”를 반드시 명시한다.

## 15. 주요 파일별 상세 메모

### `main.py`

- 최상위 전역 상수에 경로/모델이 모여 있다.
- `configure_pdf_renderer()`는 PyMuPDF가 읽을 수 있는 malformed PDF에서 MuPDF 경고가 stderr를 도배하지 않게 한다.
- `make_llms()`는 API 키를 읽고 세 개의 LLM 객체를 생성한다.
- `run_registry_workflow()`, `run_appraisal_workflow()`, `run_mortgage_workflow()`는 각각 parser 패키지를 직접 호출한다.
- `main()`은 모든 stage를 순차 실행한다. stage 2와 stage 3은 설계상 병렬 가능하지만 현재 구현은 순차 호출이다. stage 4 내부는 목록번호별 병렬이다.

### `pipeline.py`

- Pydantic 모델:
  - `RealEstateAssignment`, `RealEstateMatchDecision`
  - `RealEstateAssignmentVerification`, `RealEstateMatchVerification`
  - `MachineryItemMatch`, `MortgageListMatchDecision`
- 정규화 유틸:
  - `clean`, `registry_key`, `parse_date_tuple`, `iso_date`, `parse_money`, `normalize_shared`, `normalize_mortgagee`, `normalize_list_no`, `short_list_no`
- 파일 유틸:
  - `load_json`, `write_json`, `file_sha256`
- 주요 stage:
  - `stage1_merge_registry`
  - `stage2_real_estate`
  - `stage3_machinery_base`
  - `stage4_machinery_match`
  - `build_workbook_plan`
  - `validate_workbook_plan`

### `excel.py`

- 과거 함수 `create_collateral_distribution_workbook()`도 존재하지만 현재 통합 `main.py`는 `write_collateral_workbook()`을 사용한다.
- `write_collateral_workbook()`은 `_validate_workbook_plan()` 통과 없이는 저장하지 않는다.
- 저장은 `.tmp.xlsx`를 먼저 만든 뒤 `replace()`로 최종 파일을 교체한다.

### `matching.py`

- deterministic matching 보조 유틸이다.
- 현재 `main.py` → `pipeline.stage4_machinery_match()` 경로에서는 LLM 기반 ID 매칭을 사용하므로 `matching.py`가 핵심 경로는 아니다.
- `excel.py`에서 목록번호 정규화 함수 `normalize_list_no()`를 import한다.

### `test.py`

- 과거/참고용 parser 호출 스크립트다.
- `python main.py`의 통합 흐름과 달리 등기부/감정평가서/저당목록 parser를 순서대로 실험 호출한다.
- README 요구사항에는 `test.py` 호출 방식을 참고하라고 되어 있다.

## 16. 설계상 알려진 주의점

1. **경로가 절대경로로 하드코딩되어 있다.** 다른 머신으로 옮기면 `PROJECT_ROOT`부터 수정해야 한다.
2. **README와 현재 main 입력 케이스가 다르다.** README는 휴먼중공업 예시, 현재 main은 문화충전소/동구 초량동 예시다.
3. **output 폴더에는 여러 케이스 산출물이 섞여 있다.** 반드시 manifest 기반으로만 현재 실행 파일을 판단한다.
4. **registry/main.py에는 fallback이 있다.** 통합 실행에서 성공 경로로 사용하지 않는다.
5. **LLM 모델명은 최신성 검증 없이 코드에 하드코딩되어 있다.** 모델명 변경이 필요하면 `main.py`, `test.py`, 개별 test 파일을 함께 확인한다.
6. **문서 인식 품질은 PDF 품질에 민감하다.** contact sheet와 page image를 넣어 보완하지만, OCR/스캔 품질이 낮으면 `review_required` 또는 API 실패가 날 수 있다.
7. **Excel 양식은 코드 생성 prototype 기반이다.** `formats/*.png`는 참고자료이고, 현재 최종 생성은 별도 xlsx template을 요구하지 않는다.

## 18. 최종 인수인계 결론

이 프레임워크의 핵심은 “PDF를 LLM으로 읽고, LLM이 만든 구조화 JSON을 코드가 검증 가능한 단계별 plan으로 낮춘 뒤, plan만으로 Excel을 결정론적으로 작성한다”는 점이다.

따라서 다음 작업자는 문제를 만났을 때 아래 순서로 접근해야 한다.

```text
PDF/API 호출 문제인가?
  → parser 패키지와 structured output schema 확인
원천 JSON 추출 오류인가?
  → output/{registry,appraisal,mortgage_list} JSON 확인
등기부/감정평가/저당목록 연결 오류인가?
  → pipeline_artifacts/01~04 단계 JSON 확인
Excel 셀/서식 오류인가?
  → workbook_plan이 ok인지 먼저 확인 후 excel.py 확인
fallback으로 성공한 것처럼 보이는가?
  → 시스템 실패로 간주하고 LLM API 경로를 복구
```

최종 산출물인 `담보물배분표.xlsx`는 `workbook_validation.status=ok`와 `review_required=[]`가 확인될 때만 신뢰한다.
