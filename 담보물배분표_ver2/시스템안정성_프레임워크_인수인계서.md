# 시스템 안정성 강화 프레임워크 인수인계서

작성일: 2026-08-04  
대상 프레임워크: 담보물배분표 자동작성 v2

## 1. 핵심 원칙

이 프레임워크는 원본 PDF 3종을 반드시 LLM API로 검증·분석한 뒤에만 최종 Excel을 만든다.

절대 원칙은 다음과 같다.

1. **fallback 실행 금지**
   - 기존 JSON, fixture, 파일명 추측, 규칙 기반 대체 성공을 허용하지 않는다.
   - LLM API 호출 실패는 전체 스크립트 실패다.
   - 문서 유형 검증 실패도 전체 스크립트 실패다.
2. **입력 문서 선검증**
   - 비싼 본 분석 전에 등기부등본, 감정평가서, 공장저당법목록 PDF가 맞는지 LLM으로 확인한다.
3. **중간산출물 중심 확장 가능성**
   - 모든 주요 변환 결과는 JSON으로 남기며, 다음 agent가 RAG 챗서비스 또는 웹서비스로 확장할 수 있도록 경로와 의미를 명확히 둔다.
4. **업무 로직과 Excel 표시 분리**
   - LLM은 문서 판독·의미 매칭·서식 계획에 관여한다.
   - 금액 합계, 수량 합계, Excel 셀 작성, 검산은 코드가 결정론적으로 수행한다.

## 2. 새로 추가된 입력 검증 패키지

새 패키지:

```text
pdf_validater/
├── __init__.py
└── validater.py
```

공개 API:

```python
from pdf_validater.validater import is_registry, is_mortgaga_list, is_appraisal

# 업로드 파일 1개당 해당 함수 1개만 호출한다.
is_registry(registry_path, llm)
is_mortgaga_list(mortgaga_list_path, llm)
is_appraisal(appraisal_path, llm)
```

추가로 올바른 철자의 alias도 제공한다.

```python
from pdf_validater.validater import is_mortgage_list
```

### 2.1 API 동작

각 함수는 다음을 수행한다.

1. PDF 파일 존재 및 확장자 확인
2. supplied LangChain LLM으로 해당 PDF 1개만 첨부
3. 문서별 전용 프롬프트 실행
   - `is_registry`: 등기사항전부증명서/표제부/갑구/을구/근저당권 형식 단서
   - `is_appraisal`: 감정평가서/감정평가요약/토지·건물·기계기구 명세표 형식 단서
   - `is_mortgaga_list`: 공장 및 광업재단 저당법 제6조 목록/목록번호/변경내역표/기계기구목록 형식 단서
4. `PdfValidationResult` structured output 수신
5. `is_valid == true`, `confidence != low` 조건 확인
6. 조건 불만족 시 `ValueError` 발생으로 전체 실행 중단

중요: 이 검증기는 범용 분류기가 아니다. 파일명이나 다른 문서까지 동시에 판단하지 않고, 업로드 파일 1개에 대해 해당 문서 전용 형식 검사만 수행한다. 반드시 LLM API 호출을 수행하며, PDF 첨부 `detail`은 저비용 검사용 `low`를 사용한다.

### 2.2 출력 스키마

```json
{
  "expected_type": "registry | mortgage_list | appraisal",
  "detected_type": "registry | mortgage_list | appraisal | other | unknown",
  "is_valid": true,
  "confidence": "high | medium | low",
  "evidence": ["원문 기반 문서 유형 단서"],
  "blocking_reason": "실패 시 중단 사유"
}
```

## 3. main.py 실행 흐름 v2

현재 `python main.py`는 다음 순서로 동작한다.

```text
0. 입력 PDF 문서별 저비용 LLM 형식 검증
   ├─ REGISTRY_PDF_PATH → is_registry()         # 등기부 전용 프롬프트 1회
   ├─ APPRAISAL_PDF_PATH → is_appraisal()       # 감정평가서 전용 프롬프트 1회
   └─ MORTGAGE_LIST_PDF_PATH → is_mortgaga_list() # 저당목록 전용 프롬프트 1회

1. 등기부등본/감정평가서/공장저당법목록 PDF LLM 병렬 분석
   ├─ registry workflow
   ├─ appraisal workflow
   └─ mortgage_list workflow

2. 명시 manifest 및 단계별 산출물 생성
   ├─ run_manifest.json
   ├─ 01_registry_merge
   ├─ 02_real_estate
   ├─ 03_machinery_base
   ├─ 04_machinery_match
   └─ 05_excel/workbook_plan.json

3. gpt-5.4 서식 개선 노드 실행 및 Excel 작성
   ├─ 06_excel_format/gt_format_summary.json
   ├─ 06_excel_format/excel_format_plan.json
   ├─ 06_excel_format/excel_format_validation.json
   └─ 담보물배분표.xlsx
```

입력 검증 보고서 저장 위치:

```text
{감정평가서 stem}/pipeline_artifacts/00_input_validation/pdf_validation_report.json
```

## 5. RAG 챗서비스 확장 포인트

다음 agent가 중간산출물 기반 RAG 챗서비스를 만들 때 우선 사용할 데이터는 다음이다.

| 목적 | 권장 소스 |
| --- | --- |
| 사용자가 “입력 문서가 맞나?” 질문 | `00_input_validation/pdf_validation_report.json` |
| 등기부 표제부/을구 근거 | `output/registry/**/title.json`, `encumbrance.json` |
| 감정평가 자산/금액 근거 | `output/appraisal/*.json` |
| 저당목록 원문 출처/page | `output/mortgage_list/*.json`의 `source_pdf`, `source_pages`, `extraction_summary` |
| 부동산 그룹 매칭 설명 | `02_real_estate/real_estate_match_decisions.json`, `real_estate_match_verification.json` |
| 기계기구 O/X 근거 | `04_machinery_match/list_match_*.json`, `machinery_table_plan.json` |
| 최종 Excel 셀 생성 근거 | `05_excel/workbook_plan.json` |
| 최종 Excel 서식 근거 | `06_excel_format/excel_format_plan.json` |

RAG 설계 시 chunk key는 다음 조합을 추천한다.

```text
run_id + stage + document_type + source_path + source_pages + entity_id
```

예시:

```text
1_감정평가서_문화충전소_동구_초량동_1149_3::mortgage_list::제2024-57호::p21-27
```

## 6. 웹서비스 확장 시 주의사항

1. 업로드 직후 `pdf_validater`를 먼저 실행한다.
2. 검증 실패 문서는 본 분석 queue에 넣지 않는다.
3. 검증 성공 보고서와 evidence를 사용자에게 보여줄 수 있다.
4. 로그인/권한/배포 요구사항은 아직 확정되지 않았으므로 이 문서는 backend workflow와 데이터 계약만 다룬다.
5. 웹서비스에서도 fallback 성공은 금지해야 한다.
6. 비용과 시간이 들더라도 LLM API 검증 및 분석이 성공해야만 작업 성공으로 표기한다.

## 7. 완료 기준

현재 v2 프레임워크의 성공 조건은 다음이다.

- `pdf_validater` 3종 검증이 모두 `status=ok`
- parser 3종 LLM 분석 완료
- `workbook_plan.json`의 `status=ok`
- `workbook_validation.json`의 `errors=[]`
- `excel_format_validation.json`의 `errors=[]`
- 최종 `담보물배분표.xlsx` 생성
- 어떤 단계에서도 fallback/fixture/기존 JSON 대체 성공 없음
