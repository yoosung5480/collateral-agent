##  병렬 문서 형식 검사
```
web_service/runtime/jobs/{job_id}/uploads/
  ├── 등기부등본 저장 PDF
  ├── 감정평가서 저장 PDF
  └── 공장저당목록 저장 PDF
  │
  │ 병렬 문서 형식 검사 
  ▼
```

- 문제정의 : 우리 시스템은 아주 비싸다. 내부적으로 여러 API 호출과 작업이 있고 시간이 오래걸린다. 문제는 문서를 잘못 업로드해도 rule기반으론 내용을 파악할수 없다는것이다. 이는 비용과 관련된 문제임으로 적은 비용으로 내용을 검사할수 있어야햇다. 실수로 잘못올린 문서에 돈과 시간을 많이 할애하는건 사용자 입장에선 치명적인 불편함이 생긴다.

- 문제해결 : 그럼으로 5.4-mini 모델을 통해서 각각 등기부등본, 감정평가서, 저당목록 pdf가 맞는지 형식검사를한다. 또한 시간 지연 최소화를 위해 비동기 호출로 병렬로 구현했다.


## 등기부/감정평가서/저당목록 병렬 파싱
```
pipeline_artifacts/00_input_validation/
  └── pdf_validation_report.json
  │
  │ 등기부/감정평가서/저당목록 병렬 파싱
  ▼
```
- 문제정의 : 문서들은 노이즈가 많이 있는 "스캔본"이다. 회계-실무를 해결하기 위해서는 정확도가 가장 우선시 돼야한다.
  - 등기부등본 : 1개의 건물 및 토지일수도, 여러 건물 및 토지 정보일수도 있다. 우리는 "표제부", "을구" 데이터만 필요하다. 또한 빗금을 인식하고, 번호로 그룹핑된 채권 6, 6-1, 6-2 같은 담보설정은 하나로 묶으며, 그 내부에서도 빗금을 통해서 업데이트된 과거내역을 지우고 현재 문서기준 살아있는 정보만 추출해야한다. 이는 단순 OCR으론 빗금을 인식하지 못하고, 그냥 모든 pdf를 넣었을때는 성능 문제와 비용문제가 치명적이였다.
  - 감정평가서 : 상대적으로 쉬운문제이나, 이또한 비용문제가 치명적이다. 또한 전체를 그대로 넣으면 스캔본임으로 문서 인식도 힘들고 엄청 오래걸린다.
  - 저당목록 : 저당목록은 등기부등본 데이터와 저당목록 묶음정보가 함께있다. 배경 이미지 및 스캔본이라 단순 OCR로 인식하기 힘들뿐만이 아니라, 문서 양도 필요이상으로 많다.

- 문제해결 : 저수준 모델로 지능적 문서 슬라이싱 문서 내부에서 우리가 필요한 페이지 번호 범위만 추출해온다. 그 이후 슬라이싱된 문서를 병렬로 pdf를 이미지 인식으로 5.6-sol모델에 detail=high 옵션으로 인식하게한다.
  - 등기부등본 : 전체 스캔본에서, 각 건물 및 토지별 등기부등본으로 분해한다. 그리고 그 내부에서 또 "표제부", "을구"로 분리한다.
  - 감정평가서 : 
  - 저당목록 : "토지·건물 감정평가명세표", "기계기구 감정평가명세표" 만 pdf를 슬라이싱해온다. 
    저당목록은 아래 구조가 반복된다.
    ```
    목록번호 A <- (추출 기준)
    ├─ 목록 변경내역표
    ├─ 간지
    ├─ 목록 표지
    └─ 기계기구목록
    ```
    `간지 - 목록 표지 - 가계기구목록`, 이 구조가 반복된다.
    해당 구조들만 따로 문서 범위를 추출해온다. 


빙식 : 1차적으로 슬라이싱할때 llm은 아주 단순히 정수리스트만 반환한다. 각 섹션의 시각, 끝번호만 반환한다. 이 번호를 토대로, "pypdf"를 통해서 페이지 번호를 토대로 분리 저장한다. 그 이후 핵심 내용이 담긴 일부 문서에 대해서 최고성능 모델인 gpt-5.6-sol + detail=high로 인식하게한다.

검증 : 회계사님이 작성한 문서를 우리 json내부 저장형태로 변경했다. 그 이후 llm의 파싱결과를 대조해봤다. 또한 저당목록 같이 시스템 내에는 전부다 저장을 해야하지만, 정답지인 회계사님이 만드신 엑셀파일엔 없는 내용의 경우 직업 pdf와 눈대조를 해서 답지를 만들고 비교했다.

```
framework_output/

  └── mortgage_list/
  │
  │ 프레임워크 pipeline 단계
  ▼
pipeline_artifacts/
  ├── run_manifest.json
  ├── 01_registry_merge/
  ├── 02_real_estate/
  ├── 03_machinery_base/
  ├── 04_machinery_match/
  ├── 05_excel/workbook_plan.json
  ├── 06_excel_format/
  └── 99_cost_tracking/
```

이제 위 내용을 토대로 엑셀 명세작업을 해야한다.

문제정의 : 엑셀 테이블의 형식은 형식이 정해져있다. 담보설정현황이 같은 테이블의 경우에는 병합해서 1개의 테이블로 관리해야한다. 또한 "부동산 담보물 배분표", "기계기구 담보물 배분표", "기계기구 담보물 대조표"의 순서가 정해져있고 해당 형식이 rule기반으로 이해가능하다. 여기서 특히 가치평가액의 경우에는 내부적인 정보 대조가 중요하다. 형식 정확도 및 비용을 감소해야했다. 프롬프트 만으로 엑셀형식을 강조하기엔 엑셀 형식을 미리 알고, 이해하고있다는 이점을 살릴수도 없고 시간-비용 측면에서 더 나쁘다.

문제해결 : 현재 우리가 이해한 excel 파싱형식을 "openpyxl" 라이브러리를 이용해서 코드를 실행하면 작성할수있게 tool_call로 담보물 배분표 엑셀작성을 위한 함수들을 정의해서 등록했다. 

## 문서형식
tool_call을 기반으로 최종 생성된 엑셀파일의 정확도는 
- GPT-5.6-sol : 웹에서 work 모드로 및 "effort : 최대", 55분 소요
- Cluade : 웹에서 Opus-5, "effort : 최대", 3시간 소요
- Cluade code : Opus-5, CLI 기반 실행, 13분 소요

여기서  "Cluade code" CLI 기반 실행은 13분이 걸렸으나, 눈으로만 대조하기에도 정확도가 많이 떨어져서 평가가치가 없어서 제외했다.

셋다 동일 프롬프트로, 원본 "등기부등본", "감정평가서", "저당목록"를 입력받았다. 프롬프트 엑셀 출력형식에 대한 아주 디테일한 지침과, 각 문서에 대해서 문서의구조, 필요한문서, 각문서에서 각 테이블 대조를 위한 방식을 아주 상세하게 기술해놨다.

결과는 담보설정현황을 그중에서도 빗금은 제외하고 살아있는것만 가져오는건 기존 AI시스템만으로도 우수하다. 하지만 테이블 병합 과정에서 실수가 있고, 감정평가서를 기반으로 정확한 가치평가액을 제공하는데에는 모두다 수치 오류가 있었다. 

또한 기계기구 대조표의경우, Claude는 인식하지 못했으며, GPT는 내용은 제대로 인식햇으나 내부 대조에서 틀렸다. 

- 우리서비스결과 :
  - 총 실행시간 366초
  - 감정평가액 : 모두동일
  - 담보설정현황 : 모두동일
  - 테이블 분리 : 모두 정상 성공
  - 대조표 : 모든 내용 인식 및 모든 대조결과 동일
  - 한계점
    - 함안군을 합천군으로 첫문서 인식하는, AI성능의 문제로 해결할수 없는 부분이 있음. 
    - 비용이 아주 비쌈. 문서가 작은경우 0.4\$, 문서가 큰 경우(등기부등본이 4개의 등기부 정보를 갖는케이스), 1.1\$까지 비용증가

결론 : 내부적으로 업무 분담 및 단계절 지침이라서 아주 빠르진 않다. 그리고 책임분리성 때문에 앞부분에서의 잘못된 문서인식이 최종본까지 그대로 들어온다. 무엇보다도 비용의 문제가있다.

# 사용자 와 상호작용
위처럼 아무리 고성능 세팅 및 고도화를 해도 llm서비스는 블랙박수 구조이며, 위와같은 내부 실수에대해서 불투명하다는 문제가 있다. 이에 우리는 해당 문서 파싱 결과에 대해서

1. 요약 보고서 작성
2. 작업 산출물 기반 RAG 채팅 시스템

을 통해서 작업 내용에 대해서 회계사가 상호작용하고 실패지점 및 성공지점을 알 수 있게 구현했다. 해당 챗모델은 gpt-5.4-mini모델을 사용했으며, 최종 excel 산출물 데이터는 agent를 위한 간소화 및 정리된 프롬프트 형식으로 시스템 프롬프트로 들어가게 해서 대화에서 보고서 관련 대화에 대한 집중도를 아주 높혔다.

이 시스템 프롬프트는 중간산출물을 RAG로 연결했을때 사용자 만족도 측면에서 아주 높은 성능을 보였다.
