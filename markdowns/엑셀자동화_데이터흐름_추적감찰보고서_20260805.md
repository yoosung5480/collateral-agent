# 담보물배분표 엑셀자동화 데이터 흐름 추적 감찰 보고서

## 1. 보고서 목적

이 문서는 웹서비스에서 사용자가 업로드한 원본 PDF 3종이 어떤 경로에 저장되고, 어떤 파이썬 프레임워크 단계에서 어떤 중간산출물로 변환되며, 최종 Excel 및 RAG 보고서/채팅 산출물이 어디에 저장되는지 추적하기 위한 업무 구조도다.

대상 실행 방식:

```bash
python -m web_service.server
```

브라우저 접속:

```text
http://127.0.0.1:8000/
```

개발자 대시보드:

```text
http://127.0.0.1:8000/developer
```

## 2. 전체 실행 단위

웹서비스는 사용자 요청 1건마다 내부 `job_id`를 만든다.

```text
job_id = YYYYMMDDHHMMSS-8자리hex
```

모든 산출물은 다음 작업별 루트 아래에 격리 저장된다.

```text
web_service/runtime/jobs/{job_id}/
```

사용자 화면에는 내부 식별자인 `job_id` 대신 다음 정보를 중심으로 표시한다.

- 업로드 파일명
- 요청시간: `YYYY-MM-DD HH:MM:SS`
- 현재 처리 단계
- 진행률
- 최종 Excel 다운로드 여부

## 3. Windows 대응 파일명 정책

사용자 업로드 파일명은 `web_service/server.py`의 `sanitize_filename()`에서 저장명으로 변환된다.

처리 원칙:

1. macOS 분해형 한글(NFD)을 조합형 한글(NFC)로 정규화한다.
2. Windows 금지문자 `< > : " / \ | ? *`는 `_`로 치환한다.
3. ASCII 제어문자는 `_`로 치환한다.
4. 끝의 공백/마침표/불필요한 `_`는 제거한다.
5. `CON`, `PRN`, `AUX`, `NUL`, `COM1`~`COM9`, `LPT1`~`LPT9` 같은 Windows 예약 파일명은 앞에 `_`를 붙인다.
6. 파일명 길이는 180자 수준으로 제한한다.

예시:

| 입력 파일명 | 저장 파일명 |
| --- | --- |
| `감정평가서_문화충전소_동구 초량동 1149-3.pdf`의 macOS NFD 문자열 | `감정평가서_문화충전소_동구 초량동 1149-3.pdf` |
| `CON.pdf` | `_CON.pdf` |
| `a<b>:c"d/e\f\|g?*.pdf` | `a_b_c_d_e_f_g.pdf` |

이 정책 때문에 기존처럼 한글 자모가 정규식에서 탈락해 `_____ _ 1149-3`처럼 보이는 문제가 방지된다.

## 4. 전체 업무 구조도

```text
[브라우저]
  │
  │ POST /api/jobs

  ▼
[web_service/server.py]
  │
  │ 1. job_id 생성
  │ 2. 파일명 NFC + Windows-safe 변환
  │ 3. PDF 3종 저장
  ▼
web_service/runtime/jobs/{job_id}/uploads/
  ├── 등기부등본 저장 PDF
  ├── 감정평가서 저장 PDF
  └── 공장저당목록 저장 PDF
  │
  │ 병렬 문서 형식 검사 
  ▼
pipeline_artifacts/00_input_validation/
  └── pdf_validation_report.json
  │
  │ 등기부/감정평가서/저당목록 병렬 파싱
  ▼
framework_output/
  ├── registry/
  ├── appraisal/
  └── mortgage_list/
  │
  │ 프레임워크 pipeline 단계
  ▼
pipeline_artifacts/
  ├── run_manifest.json
  ├── 01_registry_merge/
  ├── 02_real_estate/
  ├── 03_machinery_base/
  ├── 04_machinery_match/
  ├── 05_excel/workbook_plan.json
  ├── 06_excel_format/
  └── 99_cost_tracking/
  │
  │ Excel writer
  ▼
final/담보물배분표.xlsx
  │
  │ RAG 시작 버튼 또는 첫 질의
  ▼
rag/
  ├── rag_index.json
  ├── initial_report.md
  ├── rag_usage_summary.json
  └── cost_tracking/cost_summary.json
```

## 5. 입력 API와 저장 구조

### 5.1 브라우저 → 서버 업로드 JSON

`POST /api/jobs`

```json
{
  "registry": {
    "filename": "부동산등기부등본.pdf",
    "contentBase64": "..."
  },
  "appraisal": {
    "filename": "감정평가서.pdf",
    "contentBase64": "..."
  },
  "mortgageList": {
    "filename": "공장저당목록.pdf",
    "contentBase64": "..."
  }
}
```

### 5.2 원본 업로드 저장 위치

```text
web_service/runtime/jobs/{job_id}/uploads/
```

역할별 저장명:

```text
registry       → 등기부등본 PDF
appraisal      → 감정평가서 PDF
mortgage_list  → 공장저당목록 PDF
```

서버의 `JobState.input_files`에는 실제 저장된 파일명이 기록된다.

## 7.4 pipeline_artifacts 및 framework_output 전체 RAG 인덱싱

입력:

```text
pipeline_artifacts/**/*.json
framework_output/**/*.json
```

`framework_output` JSON은 각 parser의 원본 가공이 적은 구조화 데이터이므로 RAG 소스에 포함한다. 최종 요약성 pipeline 산출물과 원본성 parser 산출물을 함께 검색하게 된다.

처리:

1. JSON 파일 탐색
2. JSON 원문을 그대로 임베딩하지 않음
3. 규칙 기반 compact text로 변환
4. 업무 단위별 청킹
5. OpenAI embedding 생성
6. local JSON vector store 저장

출력:

```text
rag/rag_index.json
rag/rag_usage_summary.json
```

`rag_usage_summary.json`에는 embedding 호출 수, embedding token, 예상 USD 비용이 기록된다.

- 단일 사용자 전제
- `thread_id`는 전역 상수로 하드코딩
- 같은 job의 RAG session 내에서 보고서와 후속 질의가 하나의 대화 흐름으로 유지됨

실패 위치별 남는 정보:

| --- | --- | --- |

| PDF 파싱 | 일부 `framework_output/*`, LLM cost summary | 파싱까지 토큰/비용 |
| pipeline 중간 단계 | 해당 단계 이전 `pipeline_artifacts/*`, cost summary | 실패 단계까지 토큰/비용 |
| Excel 생성 | `workbook_plan.json`, format 산출물 일부 가능 | Excel 직전까지 토큰/비용 |
| RAG 생성/채팅 | `rag_usage_summary.json`, RAG cost summary 일부 가능 | RAG LLM/embedding 사용량 |

## 10. 현재 제거된 차단 게이트

요청에 따라 다음 rule 기반 workbook 검증 차단을 제거했다.

| 위치 | 제거 내용 |
| --- | --- |
| `담보물배분표 _ver2/pipeline.py` | `build_workbook_plan()`에서 `validate_workbook_plan()` 호출 및 `workbook_validation.json` 생성 제거 |
| `담보물배분표 _ver2/excel.py` | `write_collateral_workbook()` 시작부의 `_validate_workbook_plan(workbook_plan)` 호출 제거 |
