# 담보물배분표 자동화 프레임워크 인수인계서

> 목적: 이 문서 하나만 읽어도 개발자와 후속 Agent가 현재 코드베이스의 구조, 실행 방식, PDF별 파싱 기준, 중간산출물, 최종 Excel 생성 방식, 비용/시간 추적 방식을 이해하고 추가 개발 또는 웹서비스 연동을 시작할 수 있게 한다.

---

## 1. 한 줄 요약

이 프레임워크는 세 가지 원본 PDF 입력값인 **등기부등본**, **감정평가서**, **공장 및 광업재단 저당법 제6조 목록(저당목록)**을 LLM과 deterministic Python 로직으로 파싱·대조한 뒤, 기존 GT 양식을 코드에 내장한 내부 규칙에 맞춘 최종 `담보물배분표.xlsx`를 생성한다. `python main.py` 실행마다 LLM 실제 토큰 사용량, 추정 달러 비용, 실행 시간이 로컬 장부에 자동 누적된다.

## 2. 실행 진입점

### 기본 실행

```bash
python main.py
```

### 핵심 전역 설정 위치

파일: `main.py`

주요 상수:

| 상수 | 의미 |
|---|---|
| `PROJECT_ROOT` | 현재 프로젝트 루트 |
| `ENV_PATH` | `.env` 경로. `OPENAI_API_KEY`를 읽는다 |
| `REGISTRY_PDF_PATH` | 등기부등본 PDF 입력 |
| `APPRAISAL_PDF_PATH` | 감정평가서 PDF 입력 |
| `MORTGAGE_LIST_PDF_PATH` | 저당목록 PDF 입력 |
| `FINAL_OUTPUT_DIR` | 실행 결과 폴더. 현재는 감정평가서 파일명 기반 |
| `FINAL_OUTPUT_PATH` | 최종 Excel 출력 경로 |
| `PIPELINE_OUTPUT_ROOT` | 단계별 중간산출물 루트 |
| `COST_TRACKING_LEDGER_DIR` | 전체 실행 누적 비용 장부 경로 |
| `COST_TRACKING_PRICING_PATH` | 달러 비용 환산용 모델 단가 JSON |

모델명:

| 상수 | 용도 |
|---|---|
| `MINI_MODEL_NAME = "gpt-5.4-mini"` | 저비용 문서 형식검사, 섹션 분할 등 |
| `SOL_MODEL_NAME = "gpt-5.6-sol"` | 본문 추출, 의미 대조, 중요 검증 |
| `FORMAT_MODEL_NAME = "gpt-5.4"` | 최종 Excel 서식 개선 plan 생성 |
| `PDF_VALIDATION_MODEL_NAME` | `.env`에서 검증 모델만 오버라이드 가능 |

중요 원칙:

- fallback 실행 금지. LLM API 호출이 실패하면 전체 실행도 실패해야 한다.
- PDF별 형식검사는 각각 독립 함수로 한 파일에 한 번씩 실행한다.
- 비용 추적은 LangSmith 추정값이 아니라 LangChain/OpenAI 응답 metadata의 실제 token usage를 사용한다.

## 4. 패키지별 기능 및 API

## 4.1 `main.py` — 오케스트레이션 계층

역할:

1. `.env` 로드 및 LLM 객체 생성
2. PDF 문서별 형식검사
3. 등기부등본·감정평가서·저당목록 병렬 파싱
4. 파싱 JSON을 pipeline stage로 병합·대조
5. Excel plan 및 내부 서식 계약 기반 LLM 서식 plan 생성
6. 최종 Excel 작성
7. 실행별 비용/시간 추적 저장

주요 API:

| 함수 | 설명 |
|---|---|
| `configure_pdf_renderer()` | PyMuPDF의 비치명적 경고 출력 억제 |
| `make_llms(cost_tracker=None)` | 검증/mini/sol/tool/format LLM 생성. cost tracker callback 연결 가능 |
| `run_registry_workflow(gpt_mini, gpt_sol, cost_tracker=None)` | 등기부등본 분할 → 표제부/을구 추출 JSON 생성 |
| `run_appraisal_workflow(gpt_mini, gpt_sol, cost_tracker=None)` | 감정평가서 섹션 분할 → 토지/건물/기계기구 JSON 생성 |
| `run_mortgage_workflow(gpt_mini, gpt_sol, cost_tracker=None)` | 저당목록 번호별 분할 → 기계기구 목록 JSON 생성 |
| `main_async()` | 전체 비동기 실행 흐름 |
| `main()` | `asyncio.run(main_async())` 진입점 |

웹서비스 연동 시에는 `main_async()`를 그대로 호출하거나, 입력 PDF 경로를 파라미터화한 서비스용 wrapper를 별도로 만들면 된다. 현재 코드는 전역 상수 기반 배치 실행 구조다.

## 4.2 `pdf_validater/` — 문서별 저비용 LLM 형식 검사기

파일: `pdf_validater/validater.py`

역할:

- 업로드 또는 입력된 각 PDF가 기대 문서 형식과 맞는지 LLM으로 선검증한다.
- 범용 `validate_pdf_type` 하나로 합치지 않고, 문서별 특징을 반영한 독립 프롬프트/독립 API를 사용한다.
- 각 파일마다 한 번씩 검사한다.

주요 API:

| 함수 | 입력 | 반환 | 설명 |
|---|---|---|---|
| `is_registry(registry_path, llm)` | 등기부등본 PDF, LLM | `PdfValidationResult` | 등기사항전부증명서/등기부등본 형식 검사 |
| `is_appraisal(appraisal_path, llm)` | 감정평가서 PDF, LLM | `PdfValidationResult` | 감정평가서 형식 검사 |
| `is_mortgaga_list(mortgaga_list_path, llm)` | 저당목록 PDF, LLM | `PdfValidationResult` | 공장저당법 제6조 목록 형식 검사. 기존 오타 API 유지 |
| `is_mortgage_list(mortgage_list_path, llm)` | 저당목록 PDF, LLM | `PdfValidationResult` | 올바른 철자 alias |
| `write_validation_report(results, output_path)` | 검사 결과 dict, 출력 경로 | dict | 검증 보고서 저장 |
| `validate_required_inputs(...)` | 3개 입력 PDF, LLM | dict | 편의 일괄 검사. 현재 `main.py`는 직접 쓰지 않음 |

검증 기준:

- 등기부등본: `등기사항전부증명서`, `[표제부]`, `[갑구]`, `[을구]`, 근저당권, 채권최고액, 접수, 권리자 등의 형식 단서.
- 감정평가서: `감정평가서`, 평가목적, 기준시점, 감정평가액, 토지·건물 감정평가명세표, 기계기구 감정평가명세표 등의 단서.
- 저당목록: `공장 및 광업재단 저당법 제6조 목록`, 목록번호, 목록 변경내역표, 기계기구목록, 명칭/규격/제작자/수량 등의 단서.

산출물:

```text
{FINAL_OUTPUT_DIR}/pipeline_artifacts/00_input_validation/pdf_validation_report.json
```

## 4.3 `registry/` — 등기부등본 파싱

주요 파일:

- `registry/pdf_llm_parser.py`: 통합 등기부 PDF를 독립 등기부 및 구역별 PDF로 분할
- `registry/parse_registry_info.py`: 분할 PDF에서 표제부와 을구 근저당권 정보 추출
- `registry/json_model.py`: Pydantic model JSON 저장 유틸

### `registry/pdf_llm_parser.py`

주요 API:

| 클래스/함수 | 설명 |
|---|---|
| `RegistrySplitPlan` | 독립 등기부 시작 페이지 목록 스키마 |
| `RegistrySectionPlan` | 표제부 페이지, 을구 페이지 목록 스키마 |
| `RawRegistryParser.async_split_registry_sections(path, output_root)` | 원본 등기부 PDF를 `registry_XX` 단위로 나누고, 각 등기부의 표제부/을구 PDF 생성 |
| `build_page_ranges(split_plan, total_pages)` | 시작 페이지 목록으로 각 등기부의 페이지 범위 계산 |
| `write_page_range(...)` | PDF 특정 범위 저장 |
| `write_selected_pages(...)` | 선택 페이지 PDF 저장 |

등기부 분할 기준:

1. 통합 PDF에서 `등기사항전부증명서` 제목, 문서 내부 페이지 번호 초기화, 고유번호/소재지 변경 등을 근거로 독립 등기부 시작 페이지를 찾는다.
2. 각 독립 등기부 PDF에서 `[표제부]`가 있는 페이지와 `[을구]` 또는 `소유권 이외의 권리에 관한 사항`이 있는 페이지를 찾는다.
3. 한 물리 페이지에 표제부 끝과 을구 시작이 같이 있으면 양쪽에 모두 포함될 수 있다.
4. 갑구, 공동담보목록, 별도 첨부 목록은 표제부/을구 본문으로 오인하지 않게 한다.

대표 산출물:

```text
output/registry/{원본파일명}/split_plan.json
output/registry/{원본파일명}/registry_01_p1-6/full.pdf
output/registry/{원본파일명}/registry_01_p1-6/title.pdf
output/registry/{원본파일명}/registry_01_p1-6/encumbrance.pdf
```

### `registry/parse_registry_info.py`

주요 API:

| 클래스/함수 | 설명 |
|---|---|
| `TitleSection` | 표제부 현재 유효 부동산 정보 스키마 |
| `Mortgage` | 을구 근저당권 스키마 |
| `EulSection` | 을구 근저당권 목록 스키마 |
| `RegistryParser.async_extract_title(source_path)` | 표제부 PDF에서 현재 유효 정보 추출 |
| `RegistryParser.async_extract_encumbrance(source_path)` | 을구 PDF에서 현재 유효 근저당권 추출 |

표제부 파싱 기준:

- 말소선, 취소선, 변경 전 과거 정보는 제외한다.
- 토지는 현재 지목/면적/소재지 정보를 추출한다.
- 건물은 현재 구조, 용도, 층별 면적 등 유효 문구를 하나의 `details` 문자열로 보존한다.
- 갑구/을구 권리 정보는 표제부 결과에 섞지 않는다.

을구 파싱 기준:

- 현재 유효한 근저당권만 추출한다.
- 말소등기 또는 해지등기가 확인된 권리는 제외한다.
- 원등기와 부기등기가 이어지는 경우 변경 내용을 원등기에 반영한다.
- `registration`은 최초 설정 접수일자를 사용한다.
- `maximum_claim`, `mortgagee`, `shared_collateral`, `mortgage_list_no`를 추출한다.

대표 산출물:

```text
output/registry/{원본파일명}/registry_01_p1-6/title.json
output/registry/{원본파일명}/registry_01_p1-6/encumbrance.json
```

## 4.4 `appraisal/` — 감정평가서 파싱

파일: `appraisal/parser.py`

역할:

- 감정평가서 PDF에서 토지/건물 감정평가 명세와 기계기구 감정평가 명세를 분리·추출한다.
- 섹션 경계는 LLM이 찾고, 추출 결과는 Pydantic 스키마로 강제한다.

주요 API:

| 클래스/함수 | 설명 |
|---|---|
| `AppraisalSectionPlan` | 토지/건물 명세 시작·끝 페이지, 기계기구 명세 시작·끝 페이지 스키마 |
| `LandBuildingAssetItem` | 토지/건물 세부 평가 행 |
| `LandBuildingGroup` | 같은 소재지/지번 기준 토지·건물 묶음 |
| `LandBuildingExtraction` | 토지/건물 추출 결과 |
| `MachineryItem` | 감정평가서 기계기구 행 |
| `MachineryExtraction` | 기계기구 추출 결과 |
| `AppraisalParser.async_invoke(path, output_root)` | 전체 감정평가서 파싱 workflow 실행 |
| `load_appraisal_json(path)` | 감정평가 JSON 로드 |

감정평가서 파싱 기준:

1. 감정평가서 전체 PDF와 contact sheet를 사용해 섹션 경계를 찾는다.
2. 토지/건물 명세표에서는 소재지, 지번, 구조/용도/면적, 평가액 등 담보물 배분에 필요한 항목을 추출한다.
3. 기계기구 명세표에서는 일련번호, 명칭, 규격, 제작자, 수량, 평가액 등을 추출한다.
4. 원문에 없는 정보는 추정하지 않는다.
5. 중간 결과에는 source page, warning, extraction summary를 남겨 추후 검토할 수 있게 한다.

대표 산출물:

```text
output/appraisal/{감정평가서파일명}/section_plan.json
output/appraisal/{감정평가서파일명}/land_building.pdf
output/appraisal/{감정평가서파일명}/machinery.pdf
output/appraisal/{감정평가서파일명}.json
```

## 4.5 `mortgage_list/` — 공장저당법 제6조 목록 파싱

파일: `mortgage_list/parser.py`

역할:

- 저당목록 PDF에서 목록번호별 묶음을 찾고, 각 목록번호 아래 현재 유효한 기계기구 목록을 추출한다.
- 앞부분에 등기부 일부가 섞여 있어도 제6조 목록 묶음이 명확하면 목록 파싱을 계속한다.

주요 API:

| 클래스/함수 | 설명 |
|---|---|
| `MortgageListSlice` | 목록번호별 시작/끝 페이지 스키마 |
| `MortgageListSplitPlan` | 목록번호별 PDF 분할 계획 |
| `MortgageMachineryItem` | 저당목록의 기계기구 품목 행 |
| `MortgageListGroup` | 목록번호 하나에 대한 기계기구 품목/warning 묶음 |
| `MortgageAssetsReport` | 전체 저당목록 파싱 결과 |
| `MortgageParser.async_invoke(path, output_root, json_path=None)` | 전체 저당목록 파싱 workflow 실행 |
| `run_mortgage_list_workflow(...)` | 비동기 workflow helper |
| `load_mortgage_assets_json(path)` | 저당목록 JSON 로드 |

저당목록 파싱 기준:

1. `공장 및 광업재단 저당법 제6조 목록 제YYYY-N호` 패턴을 기준으로 목록번호 묶음을 찾는다.
2. 목록 표지와 기계기구목록 본문을 읽어 해당 목록번호의 기계기구 품목 행만 구조화한다.
3. 변경내역, 말소/삭제 이력, 상태값은 저당목록 반환 JSON에 만들지 않는다.
4. 품목 행에서는 `list_serial_no`, `name`, `specification`, `manufacturer`, `manufactured_date`, `quantity`, `unit`, `remarks`, `source_text`를 추출한다.
5. 금액·평가액은 저당목록에서 만들지 않는다. 금액은 감정평가서 기준으로 다룬다.

대표 산출물:


## 4.6 `pipeline.py` — 중간산출물 생성, 매칭, Excel plan 작성

역할:

### 부동산 매칭 흐름

1. 등기부에서 추출한 현재 유효 표제부와 을구 근저당권을 `stage1_merge_registry`가 그룹화한다.
2. 그룹 기준은 을구 근저당권 signature다. 동일한 설정일자, 채권최고액, 근저당권자, 공동담보, 목록번호 구성을 가진 등기부를 같은 담보 그룹으로 묶는다.
3. 감정평가서의 토지/건물 평가 그룹을 만든다.
4. LLM이 등기부 그룹과 감정평가 그룹의 ID 관계만 반환한다. 금액 계산은 하지 않는다.
5. 독립 검증 LLM이 1차 매칭을 승인/거절/보류한다.
6. 일부 명확한 미배정 건물/토지는 deterministic resolver가 보정한다.
7. Python 검증이 누락, 중복, 충돌 여부를 점검한다.

### 기계기구 매칭 흐름

1. 등기부 을구 근저당권에 기재된 저당목록 번호를 읽어 기계기구 담보 그룹 후보를 만든다.
2. 감정평가서 기계기구 명세 항목과 저당목록 기계기구 품목을 목록번호별로 분리한다.
3. `async_stage4_machinery_match`가 목록번호별로 LLM 대조를 병렬 실행한다.
4. LLM은 감정평가 항목 ID와 저당목록 품목 ID의 관계, 수량, 근거, conflict만 반환한다.
5. 최종 표 값은 Python이 workbook plan으로 확정한다.

### 4.8.1 Excel 서식 LLM stage의 현재 정책

`build_excel_format_plan()`은 더 이상 `GT/담보물배분표GT.xlsx`를 읽지 않는다. 현재 runtime 입력은 `workbook_plan.json`과 `pipeline.py` 내부의 `INTERNAL_EXCEL_FORMAT_CONTRACT`뿐이다. 이 계약에는 A:P 열 너비, 표 배치 순서, 빈 행/병합/테두리 범위 원칙, 날짜/금액 표시 형식, 부산물 표 금지 원칙이 들어 있다. LLM은 이 계약을 바탕으로 제한된 `ExcelFormatPlan`만 반환하며, `excel.py`는 업무 값과 표 구조를 deterministic하게 작성한다.

산출물:

```text
pipeline_artifacts/06_excel_format/internal_format_contract.json
pipeline_artifacts/06_excel_format/excel_format_plan.json
pipeline_artifacts/06_excel_format/excel_format_validation.json
```

`cost_summary.json`의 핵심 필드:

| 필드 | 의미 |
|---|---|
| `estimated_total_cost_usd` | 한 번 실행 전체의 달러 비용 숫자 하나 |
| `elapsed_seconds` | 한 번 실행 전체 wall-clock 시간 |
| `llm_call_count` | 성공한 LLM 호출 수 |
| `llm_error_count` | 실패한 LLM 호출 수 |
| `totals.input_tokens` | 전체 입력 토큰 |
| `totals.output_tokens` | 전체 출력 토큰 |
| `totals.cached_input_tokens` | 캐시 hit 입력 토큰 |
| `totals.reasoning_tokens` | 응답 metadata에서 확인된 reasoning token |
| `totals.llm_duration_seconds` | 성공 LLM 호출 duration 합. 병렬 실행 때문에 wall-clock 시간보다 클 수 있음 |
| `by_stage` | stage별 호출 수, 토큰, 비용, LLM duration |
| `by_model` | model별 호출 수, 토큰, 비용, LLM duration |

`llm_usage_events.jsonl`의 각 줄은 LLM 호출 1개다. 주요 필드:

| 필드 | 의미 |
|---|---|
| `stage` | 호출이 발생한 처리 단계 |
| `model_name` | 실제 응답에 기록된 모델명 |
| `duration_seconds` | 해당 LLM 호출 시간 |
| `usage` | 정규화된 token usage |
| `raw_usage` | LangChain/OpenAI 원본 usage metadata |
| `estimated_cost_usd` | 해당 LLM 호출 1개의 달러 비용 |

비용 계산식:

```text
billable_input_tokens = input_tokens - cached_input_tokens
cost_usd = billable_input_tokens * input_per_1m_usd / 1,000,000
         + cached_input_tokens * cached_input_per_1m_usd / 1,000,000
         + output_tokens * output_per_1m_usd / 1,000,000
```

주의:

- 토큰 수는 실제 응답 metadata다.
- 달러 비용은 `cost_tracking/pricing.json` 단가 기준 추정치다.
- 계정별 custom pricing, 가격 변경, 장문 context pricing 정책이 다르면 `pricing.json`만 갱신하면 된다.

## 6. 웹서비스 연동 가이드

현재 구조는 local batch script다. 웹서비스로 확장할 때 권장 방식은 다음과 같다.

### 6.1 API 경계

서비스 계층에서 받을 입력:

```python
registry_pdf_path: Path
appraisal_pdf_path: Path
mortgage_list_pdf_path: Path
output_dir: Path
request_id: str
```

서비스 계층에서 반환할 출력:

```python
{
  "status": "success" | "failed",
  "request_id": "...",
  "output_xlsx_path": ".../담보물배분표.xlsx",
  "manifest_path": ".../pipeline_artifacts/run_manifest.json",
  "cost_summary_path": ".../cost_summary.json",
  "estimated_total_cost_usd": 0.123456,
  "elapsed_seconds": 123.456,
  "error": None
}
```

### 6.2 권장 리팩터링 방향

현 상태에서 웹서비스로 만들 때는 아래처럼 `main_async()` 내부 로직을 parameterized service 함수로 감싸면 된다.

```python
async def run_collateral_pipeline(
    *,
    registry_pdf_path: Path,
    appraisal_pdf_path: Path,
    mortgage_list_pdf_path: Path,
    output_dir: Path,
    request_id: str,
) -> dict:
    ...
```

주의:

- 기존 parser package의 API는 대부분 path 기반이라 웹 업로드 파일을 임시/영구 저장한 뒤 path를 넘기는 방식이 가장 단순하다.
- 비용 추적은 request_id를 `CostTracker(run_id=request_id, ...)`에 넣으면 요청별 장부가 된다.
- 절대 fallback을 두지 않는다. LLM API 실패는 HTTP 500 또는 작업 실패 상태로 노출한다.
- 장시간 실행이므로 동기 HTTP 요청보다는 background job + polling 구조가 적합하다.

### 6.3 웹서비스용 최소 상태 저장

요청별로 아래 파일을 보존하면 재현과 디버깅이 가능하다.

```text

runs/{request_id}/input/mortgage_list.pdf
runs/{request_id}/artifacts/... 중간산출물 전체
runs/{request_id}/output/담보물배분표.xlsx
runs/{request_id}/cost/cost_summary.json
```

DB에는 큰 JSON 전체보다 아래 핵심 index만 저장하면 충분하다.

| 컬럼 | 설명 |
|---|---|
| `request_id` | 실행 ID |
| `status` | queued/running/success/failed |
| `created_at`, `started_at`, `ended_at` | 시간 |
| `elapsed_seconds` | 전체 실행 시간 |
| `estimated_total_cost_usd` | 전체 추정 비용 |
| `llm_call_count` | 호출 수 |
| `input_tokens`, `output_tokens`, `total_tokens` | 토큰 합계 |

## 7. 추가 개발 시 주의사항

1. **fallback 금지**: LLM 호출 실패 시 local heuristic으로 몰래 성공 처리하지 않는다.
2. **문서별 검증 함수 유지**: `is_registry`, `is_appraisal`, `is_mortgaga_list`를 다시 범용 함수 하나로 합치지 않는다.
3. **파싱 로직과 최종 Excel 서식 로직 분리**: 데이터 추출/매칭 로직은 `pipeline.py`, 시각적 출력은 `excel.py`와 `excel_format_plan`에서 관리한다.
4. **중간산출물 보존**: 모든 stage JSON은 디버깅과 QA 근거다. 웹서비스에서도 삭제하지 않는 것이 좋다.
5. **비용 산정은 pricing file 기반**: 모델 가격이 바뀌면 코드가 아니라 `cost_tracking/pricing.json`을 우선 갱신한다.
6. **병렬성 주의**: `asyncio.gather`로 registry/appraisal/mortgage_list 및 기계기구 매칭이 병렬 실행된다. stage별 LLM duration 합은 wall-clock과 다르다.
7. **Excel 결과 검수**: 최종 출력은 `pipeline.py`의 `INTERNAL_EXCEL_FORMAT_CONTRACT`와 `excel.py`의 deterministic writer를 기준으로 해야 하며, 부산물 JSON/보조표가 최종 Excel 하단에 붙지 않도록 한다. `GT/담보물배분표GT.xlsx`는 개발 참고자료일 뿐 운영 실행에서 읽지 않는다.
